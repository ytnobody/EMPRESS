# 開発・テストの指針 — Pure Function Testing / Command Verification

> **コア原則: テストは「検証の算術」でなければならない。** 期待値を
> 実装を実行して得た出力をコピーして作るのではなく、仕様から独立に導出する。
> さもなければそれはテストではなくトートロジー（同語反復）である。

この指針は EMPRESS の Engineer がタスクを実装するときの**標準的なコーディング・
テスト規約**です。実装コードを書くときも、テストを書く/レビューするときも適用します。

---

## 常に問うべき核心の問い

どのテストにも聞く: **「これは被検コードから独立に、いったい何を検証しているのか？」**

- 期待値を「実装を実行してその出力をコピー」して作ったなら、それはテストではない。
- この問いに答えられなければ、テストを書く前に設計を直す。

## 1. ロジックを純関数に寄せる

ビジネスロジックの大半は純関数にできる。同じ入力→同じ出力、隠れた状態・I/Oなし。

- Bad: `obj.increment()` —— 内部状態を壊す
- Good: `newState = increment(state)` —— 状態を明示的な引数と戻り値に

ステートフル／状態機械も同様: `f(state, input) -> (newState, output)`。状態を明示化
すれば遷移表そのものを仕様として書き下し、検証の算術で検証できる。

**不変性も重要。** 引数で渡しても、呼び出し側が破壊的変更できては意味がない。
状態はイミュータブルなデータとして扱う。

## 2. 「何をするか決める」と「実行する」を分離する

純関数に副作用を実行させず、**副作用の記述（データ）を返させる**。

```
pure function: (state, input) -> Command    // 「何を要求すべきか」— ただのデータ
execution layer: Command -> 実際の効果        // 薄く、分岐ロジックなし
```

`Command` は手続き名＋パラメータだけの平文データ（Command パターン、Free Monad/
Interpreter パターン、Elm の Cmd と同じ発想）。

- 既定は**単一 Command**。順序効果（"DBを書き、次にメール送信"）が必要な場合のみ
  `Command[]`。必要でもないのにリスト形にしない。
- **リトライ・タイムアウト・エラー処理のロジックは純粋層（`(state, error) ->
  nextAction`）に置く。** 実行層は「指示された秒数眠る、指示された Command を呼ぶ、
  生の結果を返す」だけ。
- 重要な区別: **タイムアウトが起きるかは副作用**（実行層、検証対象外）。**起きた後の
  対処は決定**（純関数、検証対象）。「N秒後に本当にタイムアウトするか」はテストするな。
  テストするのは「既にタイムアウトが報告されたと入力として与えたとき、選ばれる
  nextAction が正しいか」だけ。

## 3. Command 検証（Command Verification）—— 副作用のテスト戦略

> 副作用を**一切実行せず**に、純関数が「正しい Command を組み立てた」ことを検証する
> —— 正しい手続き／正しいパラメータ。実行した結果を検証してはならない。

- 副作用先の正しさ（PostgresがACIDを守るか等）は相手側の責任。テストしても非決定で
  検証の算術にならない。
- 自分の責任は「正しく呼んでいるか」: 正しいクエリ、正しい bind パラメータ、正しい
  リクエストスキーマ、正しいトランザクション境界。それが Command に捕捉される。
- モック・スタブ・実呼び出し不要。`assert(buildCommand(state,input) == expectedCommand)`
  だけでよい。

## 4. DI／モックがほぼ不要になる理由

副作用を §2–3 で分離すれば、DIコンテナやモックを引っ張り出す理由の大半が消える。

- 注入するべき隠れ依存がない —— 純関数は引数で受け、データを返す。
- モックする意味がない —— DBを呼ばず、平文値を assert するから。

**DI／モックへの強い依存は症状とみなす。** それは副作用がロジックから分離されて
いないことの隠蔽である。レビューでは「この effect を Command にすれば、この DI/モック
はまだ必要か？」と問う。

失敗パターン: モックの戻り値をテスト作者が設定し、それと同じ値を assert する自己参照。
これは「実装出力を期待値にコピー」トートロジーのモック版であり、何も検証しない。

## 5. 結合テストは最小限に

検証済みの純関数の合成を内部計算で再テストする必要はない。必要がありうるのは少数:

1. **配線ミス**（引数順序・compose 順）—— 型（Newtype 等）で防げるなら型で防ぎ、
   型が表現できないものだけテスト。
2. **Core/Shell 境界そのもの** —— 真の非決定が入る唯一の継ぎ目。最小の
   smoke/契約 チェックは正当。
3. **合成順を仕様とする場合** —— 「A→B の順」自体が要件なら1〜2本の仕様テスト。

**型が強いほどこの分類は小さくなる。** 型で保証できる範囲を広げることを優先。

## 6. 実装コードにも適用する

- ロジックは既定で純関数。各関数に問う:「暗黙の依存を取るか、明示引数で受けて
  データ（効果は Command）を返すか？」
- 命令的シェルは限りなく薄く。「Command を受け取り、実行する、それだけ」。
- テストしにくいとき、真っ先に DI コンテナや interface+モックへは走らない。
  まず「テストしにくいのは、実はロジックとeffectが未分離なだけでは？」と問う。
- 状態は可変フィールドでなく、明示的・イミュータブルな引数/戻り値に。

## 7. 各テストケースに「何を検証するか」のコメントを書く

テストケースごとに、実装の仕組みに拠らず、平文で「何を検証しているか」をコメント。

- 挙動・性質を書く。「在庫がある2つの配送オプションのうち安い方を返す」—— ではなく
  「compare() を呼んでその結果を返す」。
- Command 検証テストには「どの Command を期待し、なぜか」を書く。「モックが呼ばれた」
  ではなく。
- 1行で要約できないテストは詰め込みすぎ。分割する。
- このコメントだけで、実装を消してもテストの意図が読めること（チェックリストと同じ水準）。

```
// Verifies: 状態が境界（0個）で1つ減らしても throw せず、状態は不変（冪等な下限）。
assert(remove(state0, item) == state0)
```

## 8. テストを実装より先に書く

テスト先行は、**期待値を実装の出力から導くことが構造的に不可能になる**ため、
トートロジー失敗（§4のモック自己参照と「実装出力を期待値にコピー」）を**設計的に**塞ぐ。

- 仕様から、実装本体を書く前にテスト（§7コメント付き）を書く。
- Command 検証テストなら、「どんな Command を出すべきか」をコードを書く前に決める
  —— これが Command の形（手続き名・パラメータ）の意図的な設計を強制する。
- テスト先行が難しく感じるなら、それはしばしば仕様が曖昧という信号。コードを書く
  前にそちらを解消する。
- 厳密な red-green-refactor 儀式は不問。大事なのは**順序制約（仕様→テスト→実装）**。

## 9. テストコードは要件ドキュメントの写像

テストコードは実装の副産物ではなく、**要件（自然言語）を実行可能形へ写像したもの**。

```
requirements (自然言語) --写像--> test code (実行可能)
```

具体的で確認可能な帰結:

- **被覆は全単射に近づける。** 要件↔テストが相互にトレース可能。要件のないテストは検証基盤
  が不明。テストのない要件は未検証の仕様。
- **全テストを読めば要件をほぼ再構成できる**（§7コメントがこれを可能にする）。
- **要件が変わればテストも変わる。挙動を変えないリファクタでテストを直す必要があるなら、
  テストが実装詳細に結合している**——仕様に結合していない証拠。
- **写像方向は固定: 要件→テスト→実装。** 逆に流れるなら写像が反転しており、実装なぞり
  のアンチパターンに堕ちている。

**帰結: テスト編集＝仕様変更。** テストの差分は「変わった/新発見の要件」を指して正当化
する。「実装が変わったから合わせた」は正当化にならない。レビューではテスト差分を要件文書
の差分として扱い、実装差分とは独立に説明する。

## 10. 曖昧／未確定な要件の扱い —— 黙って解決するな、マークして顕在化せよ

§8/§9 の帰結として、テスト先行・写像は「要件が既にある」ことを前提にする。しかし実際には
曖昧なことが多い。**静かに要件を捏造するのは、写像方向を反転させる**（§9への違反）。

- 要件が不明・過少指定・仮定で埋めたら、その旨を §7 コメントに明記（例:
  `// Verifies: [ASSUMPTION] 空入力をゼロでなく「invalid」と扱う — 要件文書は未指定`）。
- テストをひとまとまり書いたら、各所のマーカーを**引き継ぎリスト（handoff list）** として
  明示的にまとめ、要件の所有者に提示する。コメントに埋めるだけでなく目に見える形で。
- テスト内の仮定は**暫定**と扱い、確定・修正されたら要件文書とテストを対で更新する（§9
  より、これは正真正銘の仕様変更であり「テスト修正」ではない）。
- **自分が曖昧な点を「進めるため」に決定しそうになったら、それがまさにシグナル。** 黙って
  解釈を選ばず、この仕組みでフラグを立てる。

## 11. 要件はたいてい Level 0 —— レビュー済み設計ドキュメントを挟む

多くの要件文書は **Level 0（事業意図）** で止まり、テストに直接写像するには粗すぎる
（§10のミスをテスト作者が黙って埋めるリスク）。

```
Level 0: 要件文書 (事業意図)
              |  写像
              v
        設計ドキュメント (挙動仕様 + インターフェース仕様 — Level 1/2)
              |  レビュー (人間 or 別モデル)
              v
        テストコード (設計ドキュメントの写像)
              |
              v
        実装
```

- **設計ドキュメント**は、挙動仕様（"X が在庫なら安い方を選ぶ"）とインターフェース仕様
  （関数／Command の形。§3の Command 検証はここで根拠づけられる）を明示化する場所。
- 設計ドキュメントは、テストを書く前に**レビュー（人間、または執筆者とは別のモデル）** を
  通す。§10型の曖昧さを設計段階で拾うのが、テスト・実装後に直すより安い。
- **レビュー深さは変更の性質に応じてスケールする**（一律ではない）:
  - 些細な編集（タイポ・挙動のない整文）→ 軽く、非挙動変更だと確認して進む。
  - 特定項目への的を絞った変更 → その項目を深くレビュー（§7/§13との整合、新たな曖昧さ、
    参照する下流項目）。
  - 大規模／構造変更 → 新規設計ドキュメント同様、フル通読（hunk 単位では項目間相互作用が
    見落とされる）。
  - 不確かなら深い階層へ。コストは時間のみ、見落としは §10/§11 のリスクを再導入する。
- 一旦この中間成果物ができれば、§9 の「テストコードは要件文書の写像」はより正確には
  **「テストコードはレビュー済み設計ドキュメントの写像」** と読む。§9の帰結（テスト編集＝
  仕様変更）と §10（曖昧さを顕在化）は、テストを書く段階だけでなく設計文書を書く段階にも
  適用される。
- 設計ドキュメントが未だ無くテストを書く圧力が強いときは、**まず設計文書を書くことを優先**。
  Level 0 から直接テストを書くのが、静かな要件捏造の多くが起きる場所。

## 12. 既存（レガシー）プロジェクトへの適用 —— ストラングラー・パターン

§1–11 は目標状態。既存コードはそこから遠いことが多い。一気に書き直すのではなく、
**ストラングラー・フィグ（絡みつく木）パターン**で、レガシーの周りに規律あるコアを
少しずつ育てる。

- **手つかずのレガシーに「カバレッジのため」に特性テストを後付けするな。** 絡まった
  レガシーに対する特性テストは §1 に違反（仕様から導かず実装をなぞる）。特定部分を
  抽出/リファクタする直前に安全網としてのみ正当。
- **新規コードは §1–11 を完全適用。** 「周りがやってないから」を理由にしない。
- **触る既存コード（バグ修正・機能追加・リファクタ）では、その部分を純関数＋Command 境界
  として抽出する変更として行う**（その場パッチでなく）。これがストラングラー機構。
- 設計文書はモジュール／機能単位で部分的に導入してよい。
- 長い移行期間に2種のテストが共存するのは予期された中間状態:
  - レガシー特性テスト（実装結合・低価値、ストラングルされたら削除候補）→ `// LEGACY:`
    と明示。
  - 新規 Command 検証テスト（設計文書写像）。
- **レガシーコードから DI／モックを反射的に引き剥がさない。** 分離が先。分離後、DI は
  帰結として不要になる——その逆ではない。

> スコープ注記: この規約は**挙動の正しさ**に適用する。**非機能要件**（応答時間・スループット・
> メモリ等）は対象外で、ベンチマークの責務。性能要件を §9/§11 の写像チェーンに押し込むな。

## 13. 設計ドキュメントが真実の源、テストコメントはその写し

§7 のコメントと §11 の設計文書は重複内容を持つため、静かなドリフトを防ぐ明確な優先順位を。

> **設計ドキュメントが真実の源。§7 のテストコメントはその派生的写しであり、独立した
> 源ではない。**

- テストを変える必要があるとき（§9の帰結 = 仕様変更）、**同じ変更で対応する設計文書の項目を
  更新**する。テスト差分に設計文書差分が伴わないのは不完全。
- §7 コメントを更新したら、その源の設計文書にも同じ更新が必要かを確認。2つの成果物を
  渡る1つの編集として扱う。
- 設計文書とコメントが食い違えば設計文書が勝ち、テスト（とコメント）をそれに合わせる。
- 設計文書を一度も触らずにテストコメントばかり変えているなら、設計文書が実際の真実の源で
  なくなっている。§10型の項目としてフラグを立てる。

## レビュー用クイックチェックリスト

- [ ] 期待値は実装から独立に仕様から導出できるか（実装実行で導いたなら検証の算術ではない）
- [ ] 副作用を含むテストは、実行結果ではなく *Command* を検証しているか
- [ ] 結合テストは、型で本当に防げない配線ミス／Core-Shell境界だけか（もっと強い型で不要にできない？）
- [ ] モックを使うなら、effect を Command／データ値にすれば不要にならないか
- [ ] 実装を消しても、テストだけで何が保証されているか分かるか
- [ ] テストケースに「何を検証するか」を挙動・仕様の言葉でコメントしているか
- [ ] テストは実装より先に書かれたか（または、実装を実行せずに期待値が導出できたか）
- [ ] テストはレビュー済み設計文書（Level 0 から詳細を捏造した物ではない）にトレースされるか
- [ ] 挙動を保つリファクタ（要件変更なし）でテストは不変か
- [ ] レガシーを触る変更は、純関数＋Command境界を抽出しているか（その場パッチでない/特性テストなら LEGACY と明示）
- [ ] アサーションを変えたなら、それを正当化する明示的な要件変更があるか（「実装が変わったから」はダメ）
- [ ] アサーション／コメントを変えたなら、同じ編集で対応する設計文書項目も変わったか（§13）
- [ ] 曖昧な要件への仮定は、コメントでフラグされ引き継ぎリストにもあるか（黙って決めていないか）
