# 開発・テストの指針 — Ponytail（最小・単純の定理）

> **コア原則: 最も怠惰で、それでいて実際に動く解を。** 最も良いコードは
> 書かれなかったコードである。過剰設計・ボイラープレート・不要な依存を嫌い、
> 標準ライブラリ・ネイティブ機能・既存コードを先に使う。

これは EMPRESS の Engineer が実装するときの**最小性・単純性**の指針です。
Pure Function Testing / Command Verification（`.empress/agents/coding-guidelines.md`）
が**「何を検証するか」（正しさ・検証の算術）**を決め、Ponytail が**「何を書くか」
（最小・YAGNI）**を決めます。一緒に読んでください。

---

## はしご（ladder）—— 最初に持つ段で止まる

1. **そもそもそれが必要か？** 投機的な必要性＝スキップ、1行で「いらない」と言う。(YAGNI)
2. **このコードベースに既にある？** ヘルパー・util・型・パターンが既にあるなら再利用。
   数ファイル先にあるものを再実装するのが最よくあるスロップ。
3. **標準ライブラリに無い？** あるなら使う。
4. **ネイティブ機能がカバーする？** `<input type="date">` を picker ライブラリより、
   JSよりCSS、アプリコードよりDB制約。
5. **導入済みの依存で解ける？** 使う。数行で済むものに新しい依存は足さない。
6. **1行にできる？** 1行で。
7. **そのときだけ:** 動く最小のコード。

はしごは反射であって研究プロジェクトではない——ただし**問題を理解した上で**走らせる。
タスクと触れるコードを先に読み、実フローを端から端まで追ってから登る。2段成立したら
上の段を取って進む。最初の「怠惰で動く」解が正解。

**バグ修正＝原因、でなく対症療法でもなく原因を。** 報告された症状に手を付ける前に、
触ろうとしている関数の全callerを grep せよ。怠惰な修正＝共通関数に1つのガードを入れる
（各callerにガードを足すより小さい diff）。名前の挙がった経路だけ直すと兄弟callerは
壊れたまま残る。

## ルール

- **要請されていない抽象は作らない。** 実装1つの interface、製品1つの factory、
  変わらない値のための config。
- ボイラープレート・「後で使うための」足場はなし。後でその場で作れる。
- **削除が追加に勝る。地味が賢いより勝る**（賢さ=誰かが深夜に解読するもの）。
- ファイル数は最小に。最短の動く diff が勝ち——ただし問題を理解した上で。
  間違った場所への最小変更は怠惰ではなく2つ目のバグ。
- 複雑な依頼？ 怠惰版を出し、同じ応答で「Xをやった、Yで足りる。完全版が要るなら言って」と問う。
  既定で答えられる質問で立ち止まるな。
- stdlib の選択肢が2つ同じサイズなら、境界ケースで正しい方を取る。怠惰とは
  コードを減らすことで、頼りないアルゴリズムを選ぶことではない。
- **本当に切った角**（グローバルロック・O(n²)・弱いヒューリスティクス）には
  `ponytail:` コメントで**上限とアップグレード経路**を記す
  （`# ponytail: global lock, per-account locks if throughput matters`）。

## 出力

コードが先。次に高々3行: 何をスキップしたか、いつ足すか。エッセイ・機能ツアー・
設計ノートはなし。説明がコードより長ければ説明を消す——単純化を擁護する段落は、
一文一文が散文として忍び込ませた複雑さ。明示的に求められた説明（レポート・手順書）は
負債ではなく、全文書く。禁じられているのは要請されていない散文。

形式: `[code] → skipped: [X], add when [Y].`

## 強度

| Level | 変化 |
|---|---|
| **lite** | 依頼されたものを建てるが、怠惰な代替を1行で示す。利用者が選ぶ。 |
| **full**（既定） | はしごを強制。stdlib/ネイティブ優先。最短diff・最短説明。 |
| **ultra** | YAGNI 過激派。追加より削除。ワンライナーを出し、残りの要件に同じ息で挑戦。 |

## 怠惰でいてはいけない時

決して単純化してはならない: **信頼境界の入力検証、データ損失を防ぐエラー処理、
セキュリティ対策、アクセシビリティの基本、明示的に要求されたもの。** 利用者が完全版を
要求したら、再反論せず建てる。

**理解に対しては決して怠惰になるな。** はしごは解を短くし、読むことを短くはしない。
手を付ける前に全体を追う——触れる全ファイルと実フロー。理解を飛ばして小さなdiffを
出す怠惰は危険な種類: 自信を持った間違った修正を効率に見せかける。完全に読んでから怠惰に。

ハードウェアは紙上の理想に一致しない（実時計はドリフト、実センサはズレる）。調整ノブは
残せ——物理世界は最小モデルが看取れない調整を必要とする。

**怠惰なコードにチェックが無いのは未完成。** 非自明なロジック（分岐・ループ・パーサ・
マネー/セキュリティ経路）は **1つの実行可能なチェック** を残す——壊れたら失敗する最小の
もの。`assert` ベースの `demo()`/`__main__` 自己チェックか小さなテスト1本。フレームワーク/
fixture/関数ごとのスイートは求められない限り不要。自明なワンライナーはテスト不要——
**YAGNI はテストにも適用される**。

## ponytail-review — 過剰設計だけを見るコードレビュー

diff の不必要に複雑な部分を探す。1項目1行: 場所、何を切るか、何で置き換えるか。

### 形式

`L<line>: <tag> <what>. <replacement>.` （複数ファイルは `<file>:L<line>: ...`）

### タグ

- `delete:` 死んだコード・使われない柔軟性・投機的機能。置換: なし。
- `stdlib:` 標準ライブラリが既に持つ手作り。関数名を挙げる。
- `native:` プラットフォームが既にやる依存/コード。機能名を挙げる。
- `yagni:` 実装1つの抽象、誰も設定しない config、caller 1つのレイヤー。
- `shrink:` 同じロジックを少ない行で。短い形を見せる。

### 締め

唯一の指標: `net: -<N> lines possible.` 切るものがなければ `Lean already. Ship.` で終わる。

### 境界

過剰設計と複雑性のみ。正しさのバグ・セキュリティホール・性能はスコープ外（通常レビューへ）。
Ponytail 最小の単一スモークテスト/assert自己チェックは bloat ではなく、削除候補にしない。
修正は適用せず、列挙のみ。

## ponytail-audit — リポジトリ全体の過剰設計監査

ponytail-review をレポ全体に。全ツリーをスキャンし、最大の削減から優先順位付け。

### 狩るもの

stdlib/プラットフォームが既に持つ依存、単一実装のインターフェース、1製品のfactory、
委譲だけのラッパ、1つしかexportしないファイル、死んだ旗杢/config、手作りstdlib。

### 出力

項目ごとに1行、ランク順: `<tag> <切るもの>. <置換>. [path]`
締め: `net: -<N> lines, -<M> deps possible.` 何もなければ `Lean already. Ship.`

### 境界

過剰設計と複雑性のみ。正しさ・セキュリティ・性能は通常レビューへ。列挙のみ、適用なし。

## ponytail-debt — `ponytail:` コメントの負債台帳

Ponytail が残す意図的な短縮（`ponytail:` コメント）を台帳に回収し、デイレーが
「後で=決して」に腐るのを防ぐ。読んで報告するだけ、何も変えない。

### スキャン

リポ内のマーカーを grep（`node_modules`, `.git`, ビルド成果物は除く）。

`grep -rnE '(#|//) ?ponytail:' .`  （スタックに応じてコメント接頭辞を足す）

### 出力

マーカーごとに1行、ファイルでグループ化:

`<file>:<line>, <簡略化した内容>. ceiling: <名前付きの上限>. upgrade: <再訪のトリガ>.`

`ponytail: <ceiling>, <upgrade path>` 形式なので ceiling と trigger をそのまま取る。
**腐敗リスクのフラグ**: アップグレード経路/トリガのない `ponytail:` に `no-trigger` タグ。

締め: `<N> markers, <M> with no trigger.` 何もなければ `No ponytail: debt. Clean ledger.`

### 境界

読んで報告のみ。永続化したいなら依頼する（例: `PONYTAIL-DEBT.md` に書く）。

## Pure Function Testing との併用（EMPRESS 既定）

Ponytail と PFT は衝突しない。**観点が違うだけ**:

- **PFT** = 検証の算術（純関数、Command検証、spec導出テスト、テスト先行、設計doc）。
- **Ponytail** = 最小性（YAGNI ladder、stdlib/ネイティブ優先、抽象禁止、最短diff、`ponytail:` コメント）。

**合わせ技:** 「正しいものを最小限に作り、それを算術で検証する」。

- 設計doc（PFT §11）は **spec の写像**のための最小のもの: 挙動仕様 + Command/interface 形
  だけ。アーキテクチャ散文・機能ツアーは ponytail の禁止対象。1行テストで足るなら
  スイートを足すな（PFT §5「結合テストは最小限」と ponytail「YAGNI はテストにも」は一致）。
- 非自明ロジックは PFT に従い検証の算術で**1つのチェック**を（ponytail も「1つの
  実行可能なチェック」を要求）。
- 書いたロジックの`ponytail:` を明示し、`empress_ponytail_debt` で台帳化する。
- レビュー時、Superintendent は過剰設計観点（ponytail-review/audit）と正しさ観点（PFT）を
  分けて両方通す。

## レビュー用クイックチェックリスト

- [ ] はしごの上の段を確認したか（必要か／既存か／stdlibか／ネイティブか／導入済み依存か／1行か）
- [ ] 要請されていない抽象を足していないか（実装1つの interface・factory、変わらない config）
- [ ] diff は最短か（ただし問題を理解した上で。間違った場所の最小変更はバグ）
- [ ] 切った角に `ponytail:` コメント（上限＋アップグレード経路）を付けたか
- [ ] 非自明ロジックに**最小1つの実行可能なチェック**があるか（フレームワークのスイートは不要）
- [ ] 信頼境界の検証・データ保護・セキュリティ・アクセシビリティ・明示要求を怠っていないか
- [ ] 出力は「コード→ skipped/add when」で、要請されていない散文がないか
- [ ] review/audit は過剰設計観点（delete/stdlib/native/yagni/shrink）だけで見たか
