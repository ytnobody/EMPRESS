# 開発・テストの指針 — セキュリティレビュー

> **コア原則: セキュリティは「検証の対象」であって「おまけ」ではない。**
> 正しさ（PFT）と最小性（Ponytail）の規約に加え、**「ここは決して怠惰・妥協しては
> ならない」境界**を定義する。Ponytail の例外（信頼境界の入力検証・データ保護・
> セキュリティ対策・明示要求）を、レビューとして**体系的に**実行する。

EMPRESS の Engineer は実装時に、**Superintendent はランド前に**この規約を適用する。
`empress_vuln_check`（依存CVEの決定的スキャン）は必ず最初に回す。

---

## 1. エンジニア: 実装で絶対に妥協しないもの

- **信頼境界の入力検証** — 外部入力（ユーザ、他サービス、ファイル、env、CLI引数）が
  コードを横切る場所では、型・長さ・許容値の検証を怠らない。`sh -c` やテンプレートへ
  埋め込む前に、インジェクションポイント（コマンド/SQL/HTML/シェル/パス）を特定する。
- **秘密はコード・config・ログに永久に書かない** — API key・トークン・資格情報は環境変数
  かシークレットストアから。コミットしない。`empress.toml` には絶対に書かない
  （`TYPESAFE_API_KEY` は env）。
- **認証・認可の境界を迂回しない** — 「とりあえず誰でも通す」「チェックを消す」は
  Ponytail の対象外。認可は「デフォルト拒否」で考える。
- **エラーハンドリングがデータ損失や権限昇格を招かない** — fail-safe 側へ。
- **依存は軽視しない** — new dependency を追加するときは `empress_vuln_check` で
  既知脆弱性を確認。バージョンピン留め。
- 曖昧なセキュリティ境界（「この入力は誰が信頼できるか」）は **`[SECURITY-ASSUMPTION]`**
  としてハンドオフリストに明示し、黙って安全側に寄せた解釈をしない（§10方式）。

## 2. Superintendent: ランド前のセキュリティレビューパス

**手順:**
1. **必ず `empress_vuln_check` を先に回す**（依存CVE）。発見があれば一覧で報告。
2. diff（base...branch）を読み、**変更とそのcaller** に絞って下記カテゴリを確認する。
   全アプリの丸ごと監査はランドゲートの仕事ではない（別タスク化）。
3. 所見を1行で: `<tag>: <場所> <問題>. <対処>. [高/中/低]`
4. **HIGH/信任境界を跨ぐ所見はランドを保留**し、コメントで人間へ。修正か却下かは人間判断。
5. 所見0ならその旨を明記（「security pass: clean for this diff」）。

### タグ（レビューカテゴリ）

| タグ | 確認するもの |
|---|---|
| `auth:` | 認証の欠落・弱体化・秘密の埋め込み |
| `authz:` | 認可漏れ・horizontal/vertical privilege escalation、デフォルト許可 |
| `injection:` | コマンド/SQL/シェル/パス/テンプレートインジェクション、XSS、XXE、SSRF、シェル実行に未検証入力を渡していないか |
| `secrets:` | 鍵・トークン・資格情報のハードコード/ログ/コミット |
| `validation:` | 信頼境界での入力検証欠落（型・長さ・許容値・フォーマット） |
| `crypto:` | 自作暗号・弱ハッシュ・不適切な乱数・固定IV、平文での機微データ送受信 |
| `deser:` | 不可信データの逆シリアライズ・eval/exec 系 |
| `cors/csrf:` | CORS の無差別許可・CSRFトークン欠落 |
| `config:` | セキュリティヘッダ/CSP欠落、デバッグ/開発モードを本番に、ログに機微情報 |
| `dep:` | 依存CVE（empress_vuln_check）、古くメンテ停止の依存 |
| `opsec:` | 運用面（監視、監査、ローテーション、リトライレース、タイミング） |

### 例

```
injection: src/cli/git.js:L42 `sh -c ${testCommand}` にコンフィグ外の入力が通り得る。検証 or array形式で exec へ。 [高]
secrets: .env.example をコミット。実鍵が無いことを確認＋.gitignore 化。 [中]
validation: src/api/login.js:12 認証前にパスワード長チェック無し。制約をDB/app層で検証。 [中]
```

## 3. レビューがサボるべきでない境界線（スコープ）

- ランドゲートの対象は **「このdiffの変更 + 新たに触れる境界」**。
- 「未知のcallerから流入するもの」は、トレースできる範囲で確認。トレース不能なら
  `[SECURITY-ASSUMPTION: unknown trust boundary]` と明記して保留候補に。
- 誤検知を避ける: 実際の脅威経路が無い所見は付けない（指摘の信頼性を保つ）。
- 全アプリ監査は**タスク化**して後回し可（ランドはブロックしない）。

## 4. 依存CVE（決定的チェック `empress_vuln_check`）

- スタックを自動検出: `go.mod`→govulncheck / `package.json`+lock→`npm audit` /
  `requirements.txt|pyproject.toml`→pip-audit。対応ツールが無ければ「確認不能」を明示。
- 発見は severity 順に一覧。ランド前に必ず実行し、結果を報告に含める。

## 5. レビュー用クイックチェックリスト

- [ ] `empress_vuln_check` を実行し、依存CVEを一覧化したか
- [ ] 信頼境界を跨ぐ入力を検証しているか（インジェクション/パス/型/長さ）
- [ ] 秘密（鍵・トークン）がコード・config・ログに漏れていないか
- [ ] 認可がデフォルト拒否で、権限昇格経路が無いか
- [ ] エラー処理がデータ損失・権限昇格・fail-open を招かないか
- [ ] 機微データ（送受信・保存）で平文・自作暗号・弱ハッシュを使っていないか
- [ ] CORS/CSRF/ヘッダー/CDO 設定を妥協していないか
- [ ] セキュリティ境界の曖昧さは `[SECURITY-ASSUMPTION]` として明示したか
- [ ] HIGH/信任境界の所見はランド保留・人間判断に回したか
